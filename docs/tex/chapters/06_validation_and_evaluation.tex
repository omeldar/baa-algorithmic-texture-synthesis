\section{Evaluation Setup}

The evaluation was conducted to validate whether the implemented prototype is suitable for investigating algorithmic texture synthesis methods in procedural real-time environments. The focus is not only on the visual appearance of generated textures, but also on runtime behaviour, reproducibility, parameter controllability, and suitability for interactive use.

All raw measurement files, generated plots, and evaluation scripts are stored in the project repository. The relevant folder structure is documented in Appendix~\ref{appendix:repository-structure}.

All tests were performed with the browser-based prototype described in Chapter~5. Unless stated otherwise, WebGPU was enabled in the Brave browser. For Terrain Explorer recordings, the camera was reset before each run and auto movement was enabled to keep the scene traversal comparable.

\section{Evaluation Method}

The evaluation follows a controlled experimental approach. Each test changes one main factor where possible, while the remaining configuration stays constant. This makes it easier to isolate the influence of parameters such as view distance, terrain quality, texture reuse, or synthesis method.

The experiments are grouped into several categories. Baseline and quality tests measure the general performance of the Terrain Explorer. Scalability tests investigate the influence of scene complexity. Texture reuse tests evaluate caching behaviour. Method comparison tests compare the runtime feasibility of different synthesis approaches. Additional tests examine optimization-based approximation, reproducibility, and visual controllability.

Important measurements were repeated multiple times and aggregated using the arithmetic mean and standard deviation. This reduces the influence of temporary browser, operating system, or GPU scheduling fluctuations and makes small performance differences more reliable.

The evaluation distinguishes between online and offline suitability. GPU-based procedural and rule-based methods are tested directly in the Terrain Explorer because they are intended for interactive use. CPU-based example methods, such as Efros-Leung and Image Quilting, are evaluated separately in the Texture Synthesis Lab. The genetic algorithm optimizer is also evaluated separately, since it is intended for parameter search rather than per-frame texture generation.

Qualitative evaluation complements the measurements. Generated textures are inspected visually to assess variation, parameter controllability, and suitability for material categories such as wood, stone, terrain, or cracks. For optimization-based approximation, the target texture, initial result, and optimized result are compared side by side. All following diagrams are based on exported CSV data from the prototype and use averaged values with standard deviation or error bars where repeated measurements are available.

\section{Performance of the Procedural Environment}
\label{sec:performance_procedural_environment}

This section evaluates the runtime performance of the procedural environment under three different quality configurations: low quality, baseline, and high quality. The purpose of this experiment is to establish a performance baseline for the terrain explorer without active texture generation. This baseline is important because later experiments add procedural texture synthesis, texture reuse, and different synthesis methods on top of the same environment. By first measuring the empty environment, the additional runtime cost of these later features can be compared against a controlled reference.

The tested configurations represent different trade-offs between rendering quality and computational cost. The low quality configuration uses reduced visual detail and is intended as a lightweight setting. The baseline configuration represents the standard configuration used during development and serves as the main reference point. The high quality configuration increases the visual detail and therefore represents the most demanding setting in this experiment.

No procedural textures are generated during this test. Therefore, texture generation statistics are intentionally excluded from the runtime cost analysis. The measured texture generation time is zero for this configuration and would not provide meaningful information for this specific experiment. The aggregate summary data was used for the evaluation, while the full set of individual measurement logs is not included in the thesis document because the complete test set consists of more than 30 separate files.

\section{Scalability Tests}

The scalability test evaluates how the procedural environment behaves when the visible world size is increased. For this experiment, the view distance was changed while the remaining configuration was kept constant. Three configurations were measured: view distance 1, view distance 3, and view distance 5. Each configuration was executed ten times and the exported CSV files were averaged.

Figure~\ref{fig:view-distance-scalability} shows the effect of increasing the view distance on frame rate and runtime costs. The average frame rate decreases from approximately 109.16 FPS at view distance 1 to 101.27 FPS at view distance 3 and 88.32 FPS at view distance 5. The minimum FPS shows a stronger decrease, from 102.90 FPS to 88.00 FPS and finally 65.60 FPS. This indicates that larger view distances do not only reduce the average performance, but also increase the probability of short performance drops.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{figures/06//chapter_6_4_view_distance_scalability.png}
    \caption{Scalability of the procedural environment for increasing view distances. The upper graph shows average and minimum FPS, while the lower graph shows the corresponding runtime costs. Error bars indicate the standard deviation across ten repeated runs.}
    \label{fig:view-distance-scalability}
\end{figure}

The runtime measurements show the same trend. The average render time increases from approximately 26.55 ms at view distance 1 to 40.44 ms at view distance 3 and 52.60 ms at view distance 5. This is expected, because a larger view distance increases the amount of terrain and scene content that has to be visible and rendered. In contrast, the measured chunk generation time remains very small in all three configurations, with values around 0.04 ms on average. This suggests that the main scalability limitation in this experiment is rendering cost rather than chunk generation.

Overall, the prototype remains above the 30 FPS lower boundary in all tested view distance configurations. However, the results also show that increasing the view distance has a clear negative impact on performance. View distance 3 therefore represents a reasonable default configuration for the following experiments, because it still provides a larger visible environment while keeping the frame rate in a stable interactive range.

\section{Optimization-Based Approximation}

Optimization-based approximation was evaluated separately from the real-time texture generation tests. While the previous sections focused on generating textures efficiently during rendering, this experiment investigates whether procedural parameters can be adjusted automatically to better approximate a given target texture. For this purpose, the Wood texture model was optimized against the same target image using several different optimization configurations. The corresponding target and result images are listed in Appendix~\ref{appendix:wood-optimization-results}.

Figure~\ref{fig:wood-optimization-convergence} shows the convergence behaviour of the tested configurations. The graph plots the best similarity found so far over the optimization generations. Most configurations improve strongly during the early generations and then reach a plateau. This indicates that the optimizer is able to find useful Wood parameter combinations, but that additional iterations do not always lead to proportional improvements.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figures/06/wood_optimization_convergence_by_generation.png}
    \caption{Convergence of the Wood optimization runs. The graph shows the best similarity found so far for each configuration over the optimization generations.}
    \label{fig:wood-optimization-convergence}
\end{figure}

The best final results were achieved by the low-mutation and high-mutation configurations, with similarities of approximately 91.4\% and 91.2\%. The quality-256 configuration also reached a high similarity of 90.0\%, but with a larger output size. In contrast, the fast-preview, balanced, and high-search configurations remained around 86--87\%. This shows that more iterations or a larger population alone do not guarantee a better approximation. The mutation behaviour and the search dynamics of the optimizer have a strong influence on the final result.

Overall, the results show that optimization-based approximation can improve the matching of procedural texture parameters to a target image. However, this process is not directly comparable to real-time texture generation, because it requires many candidate textures to be generated and evaluated. Therefore, optimization is better suited as an offline parameter search method. The resulting parameters can then be reused later in the real-time environment.

\section{Visual Quality and Parameter Controllability}

Visual quality is more difficult to evaluate objectively than runtime performance. While frame rate and generation time can be measured directly, the quality of a generated texture depends on the intended material, the selected parameters, and visual judgement. Therefore, this section treats visual quality as a qualitative criterion rather than as a strict numerical result.

The Wood texture model was used as the main example for parameter controllability. Its parameters influence visible properties such as grain scale, anisotropy, warping, contrast, brightness, detail strength, and crack structures. The exported examples in Appendix~\ref{appendix:wood-parameter-examples} show how changing individual parameters affects the generated texture.

The practical goal of parameter controllability is to find settings that visually match a desired appearance. This can be done manually by adjusting parameters until the result is acceptable, or more systematically through optimization-based approximation. In both cases, the generated texture is not expected to exactly reproduce a target image, but to approximate its visual structure in a controllable way.

Overall, the results show that the implemented procedural parameters provide meaningful visual control. However, the assessment remains qualitative, because no formal user study or perceptual image metric was used in this section.

\section{Discussion}

The evaluation shows that algorithmic texture synthesis can be applied effectively in a procedural real-time environment, but its suitability depends strongly on the selected method and its complexity. The prototype allowed procedural, rule-based, and optimization-based approaches to be tested under controlled conditions and connected the generated textures to a real-time 3D scene.

The first research question concerned existing approaches and systems for algorithmic texture synthesis. The state-of-the-art analysis showed that procedural, rule-based, example-based, and optimization-based methods each serve different purposes. Existing tools provide powerful workflows, but they are often designed for production rather than controlled measurement. Therefore, the custom prototype was useful because it allowed direct control over parameters, seeds, methods, and exported evaluation data.

The second research question asked how procedural and rule-based methods can be implemented in a procedural real-time environment. The implementation shows that this is feasible by separating the Texture Synthesis Lab from the Terrain Explorer while using shared method definitions and parameters. GPU-based procedural methods such as Perlin, Simplex, and Wood are especially suitable for real-time use. Rule-based methods such as Worley can also be integrated, but the evaluation shows that runtime cost depends more on the concrete algorithm than on the category itself.

The third research question focused on optimization-based approximation. The Wood optimization experiment showed that procedural parameters can be adjusted automatically to better approximate a target texture. The convergence results show clear improvement during the early generations, followed by a plateau. This means that optimization can help find useful parameter presets, but it is not suitable as a real-time generation method because many candidate textures must be generated and evaluated.

The fourth research question compared the approaches with respect to visual quality, runtime performance, reproducibility, and controllability. Procedural methods achieved the best overall real-time suitability in the tested environment. Texture reuse and caching were also important, because they improved frame-rate stability and reduced repeated generation cost. The visual and parameter examples show that procedural parameters can create meaningful and understandable variation, although this part of the evaluation remains qualitative.

Overall, the main research question can be answered positively within the scope of the prototype. Algorithmic texture synthesis can improve variation and controllability in procedural real-time environments, especially when efficient procedural methods are combined with reuse strategies. However, scalability is limited by rendering cost, hardware performance, and algorithm complexity. Optimization-based approximation is useful as an offline support method, but not as a direct real-time technique in the current implementation.

\section{Evaluation Limitations}

The evaluation was conducted in a controlled prototype environment and therefore has several limitations. The main results are based on the desktop measurements, while additional laptop tests showed that very weak hardware is unsuitable for the more demanding real-time configurations. Therefore, the laptop results mainly serve as a practical limitation case rather than as the main comparison basis.

In addition, browser and GPU scheduling can cause small measurement fluctuations. Averaging repeated runs reduces this effect, but short drops in minimum FPS can still occur.

Finally, the experiments cover representative configurations, but not every possible parameter combination. Visual quality is also partly subjective, so the results should be interpreted as an evaluation of the prototype under controlled research conditions, not as a final benchmark of a production-ready rendering system.
