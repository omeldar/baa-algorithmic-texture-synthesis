\section{Evaluation Setup}

The evaluation was conducted to validate whether the implemented prototype is suitable for investigating algorithmic texture synthesis methods in procedural real-time environments. The main focus of the evaluation is not only the visual appearance of the generated textures, but also their runtime behaviour, reproducibility, parameter controllability, and suitability for interactive use.

All tests were performed using the browser-based research prototype described in Chapter~5. The Terrain Explorer was used for experiments in which generated textures were applied inside a procedural 3D environment. The Texture Synthesis Lab was used for isolated texture generation tests, especially for comparing individual synthesis methods and measuring generation times without the additional influence of the 3D scene.

The test environment was kept as constant as possible during the measurements. Unless stated otherwise, the tests were executed with WebGPU enabled in the Brave browser. Before each Terrain Explorer recording, the camera was reset to the same default position in order to keep the visible scene area comparable between runs. Auto movement was enabled during most Terrain Explorer tests, so that the camera moved through the procedural environment in a repeatable way while performance data was recorded.

For the Terrain Explorer tests, the same initial camera configuration was used. The camera height was set to 50 and the camera distance was set to 60. The world seed, view distance, terrain quality, texture reuse rate, and object texture assignments were varied depending on the specific experiment. This made it possible to isolate the influence of selected parameters, such as view distance or texture reuse, while keeping the remaining conditions constant.

Each Terrain Explorer recording produced timing data over a fixed measurement interval. The default recording duration was 60 seconds. For the final evaluation, important tests are repeated with a consistent recording duration where possible, so that results can be compared more reliably.

The collected data was exported from the prototype as CSV files and, where useful, as PDF reports. The CSV files form the basis for the quantitative evaluation, since they allow the recorded measurements to be processed externally and visualized in diagrams. The PDF reports were mainly used as additional documentation of individual test runs.

The evaluation uses both controlled performance measurements and qualitative inspection. Runtime-related tests are based on measured values such as frames per second, render time, texture generation time, and chunk generation time. Visual quality and parameter controllability are evaluated through side-by-side comparisons of generated textures and by analyzing whether parameter changes produce understandable and useful visual variation.

\section{Evaluation Method}

The evaluation follows a controlled experimental approach. Each test changes one main factor where possible, while the remaining configuration is kept constant. This allows the influence of individual parameters and synthesis methods to be analyzed more clearly. For example, view distance tests keep the world seed, terrain quality, camera configuration, and texture reuse rate constant while only the view distance changes. Similarly, texture reuse tests compare different reuse settings under otherwise identical scene conditions.

The measurements are grouped into several experiment categories. First, baseline and quality configuration tests are used to determine the general performance behaviour of the procedural environment. Second, scalability tests evaluate how parameters such as view distance and terrain quality influence runtime performance. Third, texture reuse and caching tests investigate whether reusing generated textures improves performance in larger scenes. Fourth, synthesis method comparison tests evaluate which texture generation approaches are suitable for real-time usage. Finally, reproducibility tests check whether identical seeds and parameter settings produce stable and repeatable results.

The main quantitative metrics used in the evaluation are average frames per second, minimum frames per second, maximum frames per second, average render time, average texture generation time, and average chunk generation time. Frames per second are used as the primary indicator for interactive performance. Render time describes the cost of rendering the current scene, while texture generation time measures the cost of generating procedural textures. Chunk generation time is used to estimate the cost of updating the procedural terrain environment while the camera moves.

For real-time feasibility, the measured texture generation times and frame rates are compared against common interactive rendering targets. A frame rate of 60 FPS corresponds to a frame budget of approximately 16.67 ms per frame. This value is used as the main target for smooth real-time interaction. A frame rate of 30 FPS, corresponding to approximately 33.33 ms per frame, is used as a lower boundary for acceptable interactive behaviour. If a synthesis method requires significantly more time than these thresholds for a single texture generation, it is considered unsuitable for direct real-time generation inside the Terrain Explorer.

Important measurements are repeated multiple times to reduce the influence of temporary browser, operating system, or GPU scheduling fluctuations. For final comparisons, repeated runs are aggregated by calculating the arithmetic mean and standard deviation. This is especially important for tests where the measured differences are small, for example between similar texture reuse settings or between GPU-based procedural methods. In these cases, relying on a single run would not be sufficient to make a reliable comparison.

The evaluation also distinguishes between online and offline suitability. GPU-based procedural and rule-based methods are evaluated directly in the Terrain Explorer because they are intended for interactive use. CPU-based example methods, such as Efros-Leung and Image Quilting, are evaluated separately in the Texture Synthesis Lab. Their generation times are compared against the real-time frame budget to determine whether they are feasible for direct runtime use. The genetic algorithm optimizer is also evaluated separately, since it is designed for parameter discovery rather than per-frame texture generation.

Qualitative evaluation is used to complement the quantitative measurements. Generated textures are inspected visually to assess whether they show meaningful variation, whether parameter changes produce understandable effects, and whether the generated patterns are suitable for typical material categories such as wood, stone, terrain, or cracks. For optimization-based approximation, the target texture, the initial generated texture, and the optimized result are compared side by side. This visual comparison is important because numerical similarity alone does not fully describe perceived texture quality.

All diagrams in the following sections are based on the exported CSV data from the prototype. Where repeated measurements are available, the graphs show averaged values and, where useful, standard deviation or error bars. This makes it possible to distinguish stable performance trends from measurement noise.
