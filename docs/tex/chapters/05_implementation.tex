This chapter describes the practical realization of the research prototype. It explains the goals of the system, the chosen technology stack, the overall architecture, and the concrete implementation of the procedural environment, the texture synthesis methods, the optimization approach, and the experimental infrastructure used to evaluate them. The aim is to show how the conceptual ideas from the previous chapters were turned into a working, measurable application.

WebGPU was selected for procedural generation because it allows shader code (written in WGSL) to run massively in parallel on the GPU, which is essential for real-time texture generation. Example-based methods, which are inherently sequential, are instead executed on the CPU inside Web Workers so the user interface remains responsive during long computations.

\subsection{High-Level System Architecture}

The system is divided into two cooperating modules that share a common set of texture definitions and a common seeding mechanism:

\begin{itemize}
    \item \textbf{Texture Synthesis Lab}: selects a method, edits its parameters, previews the result, and records generation metrics.
    \item \textbf{Terrain Explorer}: applies generated textures to a procedural 3D world and records runtime performance.
\end{itemize}

A central \texttt{texture-types} module defines every method, its category, and its adjustable parameters. This single source of truth drives both the parameter UI and the generation pipelines, ensuring that the Lab and the Explorer always interpret a method identically.

\subsection{Texture Generation Data Flow}

When the user selects a texture method, the application loads the corresponding method definition from the shared texture-definition module. This definition contains the parameter identifiers, default values, value ranges, the classification category, and the rendering backend. From this definition the user interface automatically generates the matching control elements, so no method-specific UI code is required.

\begin{figure}[H]
    \centering
    \img[width=1\textwidth]{figures/05/dataflow-seq-dia.png}
    {Sequence diagram of the texture generation workflow.}
    \label{fig:dataflow-seq-dia}
\end{figure}

Whenever a parameter changes, the current parameter set together with the active seed is forwarded to the selected generation pipeline. The system dispatches the request based on whether the method has a GPU shader implementation: procedural methods are routed to the WebGPU shader pipeline, while example-based methods are executed inside a Web Worker. The generated result is then either shown as a preview in the Texture Synthesis Lab or assigned to material slots inside the Terrain Explorer. Because both consumers read from the same definition, a method only has to be implemented once.

\section{Procedural Environment Foundation}

Before describing the procedural environment, it is important to clarify its role in this thesis. The terrain and scene composition are not the main research focus, but serve as a controlled testbed for evaluating texture synthesis methods under real-time conditions. This 3D environment provides a practical context in which generated textures can be applied, measured, and compared with respect to frame rate, scalability, and caching behaviour.

\subsection{Terrain Generation}

The 3D environment is an infinite, procedurally generated landscape. Terrain height is computed entirely from layered noise functions, with no stored height maps. Several noise layers are combined to produce believable geography:

\begin{itemize}[noitemsep, topsep=0pt]
    \item \textbf{Continental shape}: low-frequency fractal Brownian motion (fBm) for large landmasses.
    \item \textbf{Mountains}: ridged noise masked by a separate low-frequency field so peaks only appear in certain regions.
    \item \textbf{Hills and details}: higher-frequency fBm layers for medium and fine variation.
    \item \textbf{Erosion}: turbulence subtracted from the surface to carve valleys.
\end{itemize}

The following simplified excerpt shows how these layers are summed into a single height value:

\begin{lstlisting}[style=defaultcode, caption={Multi-octave terrain height function combining continental, mountain, hill, and erosion layers.}, label={lst:terrain-generation-code-example}]
function getTerrainHeight(x: number, z: number, seed: number): number {
    const continental = fbm(x * 0.003, z * 0.003, seed, 5) * 30
    const mountains   = ridgeNoise(x * 0.02, z * 0.02, seed + 1000, 5)
                        * Math.max(0, fbm(x * 0.008, z * 0.008, seed + 5000, 
                        3) + 0.2) * 35
    const hills       = fbm(x * 0.04, z * 0.04, seed + 2000, 4) * 10
    const erosion     = -turbulence(x * 0.015, z * 0.015, seed + 4000, 4) * 8
    return continental + mountains + hills + erosion + 10
}
\end{lstlisting}

\subsection{Object Placement and Scene Composition}

On top of the terrain, the scene is populated with objects such as trees, rocks, and grass. Their positions are derived from the same seeded noise system, so object placement is also reproducible. Each object exposes one or more \textbf{texture slots} (for example, a tree has a trunk slot), and each slot can be assigned a generated texture.

This composition is what makes the prototype useful for comparison: the same scene can be re-textured with different synthesis methods, isolating the effect of the texture method from every other variable.

\subsection{Real-Time Rendering Pipeline}

Rendering is handled by React Three Fiber, a declarative wrapper around three.js. The world is divided into chunks that are generated and discarded as the camera moves, giving the impression of an endless landscape while keeping the number of active meshes bounded. Procedural textures are generated on the GPU and applied directly as material maps, while the renderer loop continuously reports frame timing to the measurement system described in Section~\ref{sec:measurement-system}.

\subsection{Implemented Procedural Methods}

The three procedural methods are implemented as WGSL fragment shaders that run on the GPU. They generate textures purely from mathematical functions and a seed, with no input image.

\begin{itemize}
    \item \textbf{Perlin Noise}: the classic gradient noise, exposed through scale, octaves, persistence, and lacunarity parameters. It forms the conceptual foundation for the other procedural methods.
    \item \textbf{Simplex Noise}: an improved gradient noise with fewer directional artifacts, offering contrast, brightness, and domain-warp controls.
    \item \textbf{Wood}: the most complex procedural shader, combining several techniques to imitate real wood grain: anisotropic coordinate compression, domain warping, multi-octave fBm, ridged noise for grooves, and Worley-based surface cracks. It exposes sixteen parameters, including two configurable end colors.
\end{itemize}

Because all three run on the GPU, generation is effectively instantaneous, which is what makes them suitable for real-time use.

\subsubsection{Wood Grain Shader Implementation}

The Wood shader is implemented as a layered procedural model evaluated once per output texel. First, the texture coordinates are scaled by a grain factor and compressed along one axis (anisotropy) to imitate the directional fibre structure of wood. To avoid perfectly regular, artificial-looking rings, domain warping is applied before the pattern is evaluated: a primary warp displaces the coordinate based on a low-frequency fBm value, and a secondaryt, smaller warp adds organic irregularity.

On the warped coordinates, a base structure is generated using fractal Brownian motion (fBm), which sums several octaves of Perlin noise with decreasing amplitude and increasing frequency. A ridged-noise layer is added on top to create the darker groove and grain lines, and a high-frequency fBm layer introduces fine fibre detail. An optional cellular (Worley) component subtracts crack-like features by measuring the distance to the nearest feature point in a \texttt{3x3} cell neighbourhood. Finally, the scalar pattern value is contrast-shaped and brightness-adjusted, then mapped between two configurable colors, with a subtle low-frequency modulation added for additional realism.

A detailed diagram can be found in Appendix~\ref{app:appendix-woodgrain-flowchart}, Figure~\ref{fig:woodgrain-flowchart}.

\begin{lstlisting}[style=defaultcode, caption={Core of the Wood fragment shader (WGSL, abbreviated). Domain-warped fBm is combined with ridged noise, fine detail, and Worley-based cracks before contrast shaping and two-color mapping.}, label={lst:core-wood-fragment-shader}]
// Anisotropic coordinates + domain warp
var p = uv * GRAIN_SCALE;
p.x *= ANISOTROPY;
let warp1 = fbm(vec2f(p.y * WARP_SCALE, 0.0), 3);
p.x += warp1 * WARP_STRENGTH;

// Layered structure
var wood = fbm(p, NUM_OCTAVES);                 // base grain
wood += ridgedFbm(p * 1.5, 3) * RIDGE_STRENGTH; // grooves
wood += fbm(p * 4.0, 2) * DETAIL_STRENGTH;      // fine fibres
wood -= pow(1.0 - worley(p * CRACK_SCALE), 3.0) * CRACK_STRENGTH; // cracks

// Shaping + color
wood = pow(clamp(wood * 0.5 + 0.5, 0.0, 1.0), CONTRAST);
let color = mix(COLOR_DARK, COLOR_LIGHT, wood);
\end{lstlisting}

\subsection{Rule-Based Texture Models}

The rule-based category is represented by Worley Cracks. Instead of blending gradients like Perlin or Simplex, it distributes cell centers (Voronoi sites) and applies rules about edges between cells. Parameters such as edge width, edge sharpness, and cell variation control how the boundaries between cells are rendered, producing crack and mosaic patterns suitable for stone, dried earth, or cracked surfaces.

This method illustrates a different design philosophy: where procedural noise produces continuous organic fields, rule-based generation reasons about discrete structural elements and the rules that govern their appearance.

\subsection{Texture Approximation and Optimization Concepts}

The example-based and optimization methods address a different question: \textit{how closely can a generated texture match a given target image?}

\begin{itemize}
    \item \textbf{Efros-Leung} synthesizes a texture pixel by pixel, choosing each new pixel by searching the source image for neighborhoods that resemble the already-synthesized surroundings. It is faithful but computationally expensive.
    \item \textbf{Image-Quilting} works with patches rather than single pixels. It copies overlapping blocks from the source and stitches them along a minimum-error boundary cut, which is considerably faster while preserving larger structures.
    \item \textbf{Optimization-Based} synthesis takes a fundamentally different route: instead of copying from the image, it searches for the procedural parameters (currently of the Wood shader) that best reproduce the target. This is implemented as a genetic algorithm.
\end{itemize}

The genetic algorithm maintains a population of candidate parameter sets and evolves them over many generations using selection, crossover, and mutation. Quality is measured by a fitness function that compares the generated texture against the target using several image statistics:

\section{Performance and Scalability Considerations}

\subsection{Runtime Challenges}

The central runtime challenge is that the methods have radically different cost profiles. Procedural shaders generate a texture in well under a millisecond on the GPU, whereas the example-based methods are sequential CPU algorithms that may take several seconds for a single texture. In a real-time environment that must maintain roughly 60 frames per second (a budget of about 16 milliseconds per frame), this difference determines which methods are usable at runtime at all.

\subsection{Optimization Strategies}

Several strategies keep the application responsive:

\begin{itemize}
    \item \textbf{GPU offloading}: all procedural and rule-based generation runs in parallel on the GPU.
    \item \textbf{Web Workers}: slow CPU methods run on background threads so the UI never freezes.
    \item \textbf{Chunked terrain}: only nearby world chunks are kept active, bounding memory and draw calls.
    \item \textbf{Texture reuse}: objects can share a generated texture by chunking their seeds, so a single texture is generated once and reused across many similar objects, dramatically reducing generation cost while preserving visual variety.
\end{itemize}

\subsection{Known Limitations and Technical Constraints}

\begin{itemize}
    \item WebGPU is required for procedural generation, which currently limits full functionality to Chromium-based browsers.
    \item The example-based methods are too slow for real-time use and are restricted to modest output resolutions.
    \item The optimization approach currently targets only the Wood shader.
    \item The fitness function relies on statistical rather than perceptual similarity measures.
\end{itemize}

\subsection{Texture Reuse and Caching Strategy}

Without reuse, every object and every terrain chunk could trigger a seperate texture or material creation, which becomes expensive when many objects share visually similar materials. The prototype reduces this cost with two complementary caches. Materials are keyed by their full parameter set (algorithm, scale, octaves, colors, seed, variance, roughness, and so on). When an identical key is requested, the existing material is returned instead of building a new one. Terrain chunk geometries are cached analogously by chunk coordinates, world seed, and resolution, which avoids rebuilding geometry when the player revisits a chunk. Both caches are bounded (materials to 500 entries, geometries to 200) and evict the oldest entry when full.

Variation is still preserved through a configurable texture-reuse rate. At a rate of one, every object receives a unique seed. At higher rates the seed is quantised so that groups of objects deliberately share the same texture. This exposes the trade-off between visual variety and generation cost directly as a measurable parameter in the evaluation.

\subsection{Reproducibility and Controlled Experiments}

Reproducibility is enforced through a shared seeded random-number generator used by terrain, object placement, and texture generation alike. Given the same seed and parameters, the prototype reproduces an identical world and identical textures. To support controlled experiments, complete environment configurations can be saved and reloaded, and all summary reports (PDF) and raw, self-documenting timing data (CSV) can be exported for external analysis. This allows each experiment to be repeated exactly and the resulting data to be examined independently of the application.

Building on these saved configurations, the prototype additionally automates the repeated execution of experiments, so that statistically meaningful measurements can be gathered without manual supervision, as described in the following section.

\subsection{Automated Batch Execution and Experiment Queuing}

A single recording captures only one 60-second sample of one configuration. This is not enough for a reliable evaluation, because runtime metrics like frame rate and generation time are affected by measurement noise from browser scheduling and GPU behaviour. In addition, the research questions require the same metrics across several different configurations to compare them with each other. Doing this by hand is slow and error-prone, so two levels of automation were added: repeating one configuration (batch runs) and running many configurations after each other (experiment queuing).

A batch executes the same frozen configuration several times in a row (one, five, or ten runs). Between the runs the environment is reset deterministically from the stored seed, so every run starts from the same state. This turns a single observation into a small distribution and gives an estimate of the measurement variance. The queue extends this idea to many configurations: each uploaded configuration is applied to the environment, given a short moment to settle, and then recorded as a full batch, before the queue automatically continues with the next one. Because such a series can easily take more than an hour, it can be started once and left running unattended.

Long unattended runs introduced one reliability problem. The first version kept the per-frame samples of every run in memory until the whole queue had finished, which made the data grow without bound and eventually crashed the browser tab before any result could be saved. The solution is \textit{checkpointing}, which works as follows:

\begin{enumerate}
    \item when a configuration finishes, its complete results are exported immediately as one self-contained archive,
    \item afterwards the heavy per-frame samples of that configuration are released, and only a small numeric summary stays in memory,
    \item at the end, all summaries are combined into one comparison index that shows the averaged metrics of every configuration next to each other.
\end{enumerate}

This keeps the memory usage bounded by a single configuration instead of the whole queue, and it also makes sure that the results of every finished configuration are already saved. So even if the application crashes during a later configuration, the earlier ones are not lost.

\section{Summary of the Implementation}

The implemented prototype fulfills its role as a research instrument. It combines a deterministic procedural 3D environment, seven texture synthesis methods spanning procedural, rule-based, example-based, and optimization-based categories, and a built-in measurement and reporting system. GPU-based procedural methods provide instantaneous generation. Rule-based generation demonstrates structural pattern control, and the example-based and optimization methods make it possible to study how closely algorithmic textures can approximate a target. With reproducible seeding, configurable experiments, and exportable metrics, the prototype provides the controlled and measurable foundation required for the evaluation presented in the following chapter.
